# Architecture

## Agent Tools topology

```text
Codex or another MCP host
          │ stdio MCP
          ▼
Stage5 Browser MCP server
          │
          ├── Agent Lounge service
          │       │ worker-thread RPC
          │       ▼
          │   shared local SQLite WAL
          │
          └── browser supervisor
                  ├── serialized operation queue
                  ├── hard deadlines
                  ├── privacy-minimized journal
                  ├── privacy-safe execution telemetry
                  └── worker lifecycle supervision
                              │ Node IPC
                              ▼
                       browser worker
                              │ Playwright protocol
                              ▼
                selected Playwright browser backend
                              │
                              ▼
                  dedicated persistent profile
```

## Composable browser action system

Stage5 Browser is the physical hand of an agent, not a collection of website scripts. The agent supplies authorized intent and semantic judgment; the runtime supplies a broad, reusable movement vocabulary, exact target binding, bounded force, proprioception, and recovery. A new site should normally be handled by composing existing techniques. A new primitive belongs at a generic manager boundary only when a disposable fixture proves that the hand is physically unable to express the required motion or observation.

Every worker command has exactly one owner in `src/protocol/command-contracts.ts`, including its phase system, dispatch class, and replay rule. Every public MCP tool has exactly one owner in `src/mcp/tool-contracts.ts`; its name comes from the canonical catalog in `src/mcp/tool-names.ts`. `src/protocol/capabilities.ts` is the source of truth for manager responsibilities, the non-overlapping technique vocabulary, context layers, and the shared action loop. Compile-time contracts and `tests/command-manager-contract.test.ts` prevent an unowned command, tool, or manager family from entering the product.

| Manager | Generic action family |
| --- | --- |
| lifecycle | browser runtime, isolated profile, process ownership, start/switch/stop |
| perception | bounded status, diagnostics, page events, semantic/visual/text/frame observation |
| navigation | URL open, new tab, history, reload, readiness, URL reconciliation |
| tab | stable identities, selection, activation, passive inspection, exact restoration/close |
| interaction | click, hover, focus, key press, double/context click, drag, horizontal/vertical scroll |
| form | redacted summary, text/date fill, option inspection, single/multi-select, checked state, staged plans |
| transfer | observed file input, upload evidence, durable private download capture |
| dialog | expected and unexpected alert, confirm, prompt, and before-unload handling |
| private handoff | field-scoped private input and same-profile authentication handoff |
| policy | optional deterministic action class plus agent-declared semantic intent |
| recovery | reservations, terminal status, deadlines, worker handoff, proven-zero-input recovery |
| telemetry | audited manager, phase, dispatch, reconciliation, timing, and terminal outcome evidence |
| coordination | Lounge identity, delivery, acknowledgement, presence, notice, and audited history |

The vocabulary is deliberately compositional. For example, an unfamiliar virtualized dropdown is not a new site adapter: perceive the exact control, inspect its options, prepare its owned popup and scroll surface, select one exact option, and reconcile selected/closed state. Agent discretion resolves what an option means within the user's authority; deterministic code resolves which node it is, whether it is actionable, whether input occurred, and what state resulted. No URL, label, selector, regex, or site name may stand in for business intent.

The hand is positional rather than encyclopedic. It does not try to predict every website move; before applying force it narrows the browser into a controllable position with one exact owner, one reachable input mechanism, one dispatch gate, and one observable effect. Pointer reach requires viewport contact. An exact native button may instead use keyboard reach only behind a non-null bounded postcondition. Popup discovery treats semantic list/menu/tree surfaces as primary and admits an otherwise generic option group only behind a positioned, popover, or dialog portal boundary. One broad portal may be partitioned into strict option branches only when bounded layout proves a real gap; contiguous wrappers stay together. Ownership then prefers explicit/structural relations, followed by focused, expanded, and spatial tiers. When several candidates survive one non-structural tier, only a decisive normalized edge-gap lead establishes the owner; an exact or near tie fails with zero input. In the weakest spatial tier, the popup's own bounded hit-test path may prove that a material rectangle overlap is a covered sibling rather than an equal anchor, but only one tightly adjacent exterior candidate may benefit and stronger evidence is never displaced. These generic constraints increase mobility while limiting the page's possible responses.

Consequential physical input follows one canonical loop:

```text
observe → plan → preflight → prepare → dispatch once → reconcile → finalize
                         └── one bounded recovery only after proven zero input
```

The phase session owns one absolute deadline and records the exact dispatch state. Reversible preparation may be repeated only before input. Proven zero input may authorize one recovery through fresh planning; possible or confirmed input proceeds to reconciliation and is never replayed. Specialized lifecycle, navigation, handoff, scrolling, and supervisor state machines use the same evidence principles while retaining transitions appropriate to their domains.

An opaque snapshot ref is a one-use motor capability, not merely an accessible-name query. Ref actions retain the exact node before page preparation and revalidate that same DOM identity afterward. If the node was replaced, the fallback first searches only its privacy-fingerprinted semantic owner—an article, table row, or list item—before considering the retained snapshot scope. This preserves deterministic within-row action while continuing to fail closed when either the owner or descendant is ambiguous. Click and motion share this resolver.

### Scoped context and persistence

The controller runtime is the sole mutable session-context owner. Context narrows as work approaches physical input:

| Layer | Lifetime and examples |
| --- | --- |
| durable | agent-scoped selected backend and explicit review policy, ownership lease, terminal operation journal and execution traces, Lounge state, sanitized download/dialog/page-lifecycle manifests |
| session | controlled browser identity, selected page, stable tab IDs, handoff state |
| document | frame/document versions and one-use snapshot, scroll, form, and option capabilities |
| action | absolute deadline, phase transitions, exact prepared handles, dispatch and postcondition evidence |
| private ephemeral | fill/prompt/private-field/authentication values consumed only at the dispatch or human boundary |

Only privacy-minimized records cross the durable boundary. The stable Lounge identity keys a hashed per-agent context containing only a browser enum and optional `normal`/`review_only` policy; it never contains URLs, tabs, page content, form values, external account identity, or browser handles. Agent identity, Stage5 profile ownership, and the human/account authorized for an external service remain distinct boundaries. Multiple people may use different consoles for the same service, so a signed-in page never transfers authority across users or tasks. Browser objects, element handles, refs, rendered state, and dispatch probes are always re-observed at their owning scope. Private values never become shared context, journals, diagnostics, telemetry, Lounge messages, or recovery material. This boundary makes persistence useful for continuity without turning stale state into a second source of truth.

### Audit the hand without recording the task

The supervisor writes a bounded `0600` JSONL execution trace after each terminal browser or recovery operation. The stable Lounge agent ID is included when that MCP connection has bound one, and the `operationId` joins the trace to the separately durable operation result. Display names and providers are not retained. The command contracts supply the responsible manager, phase system, dispatch class, and replay rule; the owning worker phase manager supplies transitions and dispatch attempts; sanitized canonical results supply only boolean or categorical reconciliation conclusions. This lets a developer prove which agent invoked which part of Stage5 and whether it observed, prepared, dispatched, reconciled, recovered, or failed without trusting an agent summary.

Telemetry is an allowlist, not a redaction pass over arguments. It never copies command payloads, URLs, selectors, accessible names, values, page content, coordinates, headers, bodies, queries, fragments, credentials, or private handoff data. A string-valued postcondition observation is retained only as `redacted_string`. Partial-effect reconciliation publishes the same canonical categorical check list as ordinary postconditions, so a failed click cannot silently lose what the hand measured after contact. Viewport preparation records only attempts, movement count, horizontal/vertical movement, nested/document surface class, composed-boundary traversal, and the final in-viewport boolean. Exact-target state may add categorical viewport proof and pointer-hit class; control inspection may add categorical popup association/surface proof, bounded rendered-surface and owner-class counts, the owner proof tier, and a decision category. These are the hand's proprioception, not page geometry. Rotation keeps the journal bounded, and telemetry I/O failure cannot replace the browser operation's canonical outcome. `browser_execution_traces` queries the newest bounded records globally or by exact operation ID. Because extraction and journaling run in the long-lived MCP host, adding a retained field or changing its privacy parser increments the host behavior contract and requires a fresh-host integration test; worker hot replacement alone cannot change an already-loaded trace allowlist.

## Boundary decisions

### Keep agent coordination out of the browser queue

The Agent Lounge is a separate MCP-side coordination plane. Every MCP connection binds one stable agent identity, while a shared SQLite WAL stores room membership, messages, recipient delivery state, acknowledgements, revisioned pinned notices, manager-history audit metadata, and short presence leases. That join also binds the privacy-minimized per-agent browser context on its own short serialization lane. Restored backend/policy state is reconciled inside the browser queue only when the next browser operation begins. Synchronous database and context-store access therefore cannot enter or wait behind the browser supervisor's serialized queue, consume a browser operation deadline, or make a hung browser silence coordination.

Delivery is durable and at least once until acknowledgement. Sends require idempotency keys, broadcasts snapshot current room membership, and acknowledgement states advance monotonically from delivered to seen to acted. A locally configured manager may compare-and-set the room notice or page through all room messages; notice mutations are revisioned and idempotent, while history reads append metadata-only audits and do not touch delivery state. A live bounded `lounge_wait` is the only wakeable online state; either a message or notice revision can end it. After it returns or times out, the agent renews while collaborative work remains active. Browser-worker replacement stays below this MCP-side binding and cannot clear it; `lounge_not_joined` therefore identifies a new or never-joined MCP connection. If an agent task has ended, MCP cannot restart the model, so messages remain queued until that identity joins and waits again.

The Lounge is coordination-only. Its messages carry no user authority, never expand a recipient's permissions, and exclude secrets, credentials, private form values, identity documents, payment details, tax identifiers, and chain-of-thought.

### Own the worker process

The MCP server and browser runtime are separate processes. A timeout enforced inside the same event loop cannot recover from that event loop becoming stuck. The supervisor therefore owns the worker process and can terminate its complete process group before replacement.

The separation has an explicit version boundary. MCP and worker exchange the package and protocol versions during initialization. Completed builds publish a final build stamp only after TypeScript output succeeds, so a live process never treats half-written output as current.

The resident MCP process compares the published worker protocol and tool-catalog versions with the contract it loaded. Exact build fingerprints identify artifacts for diagnostics but do not define compatibility. When both contracts are unchanged, the supervisor adopts the completed artifact identity, replaces its worker automatically, and restores the active URL on the next browser operation. This also applies when the old worker exits during a deferred private handoff. No MCP reconnect or local deployment is required for ordinary runtime fixes. It returns `MCP_RESTART_REQUIRED` only when the tool catalog or MCP-to-worker protocol actually changes. Browser actions then fail closed until reconnect, while the already-loaded Lounge join/send/wait/ack/status methods remain available because their coordination-only store and worker thread do not cross the browser command contract.

On macOS, selected-page activation has separate renderer and native-process boundaries. Stage5 resolves the exact Chromium window through CDP and the exact Stage5-owned application through its proven process identity. A hidden application is explicitly unhidden, all windows in only that owned process are activated, and the target page is reselected. AppKit request acceptance is retained as evidence but never treated as proof that the process is frontmost or that the renderer is visible. If that request leaves an already-unhidden owned process non-frontmost, one bounded Process Manager fallback targets only the same proven PID and reports process resolution, request outcome, and observed foreground state separately. It does not claim user activity or identify an application by bundle, name, title, or geometry. Input remains blocked until the final renderer observation is `visible`.

### Use an owned browser, with same-process Chromium attachment only for authentication

Normal work launches the dedicated browser through Playwright for the highest-fidelity connection and unambiguous ownership. Chromium authentication is the deliberate exception: Stage5 launches its own dedicated native process, leaves it uncontrolled while the user signs in, then connects through a loopback-only CDP endpoint without restarting that process. It never attaches to the user's everyday browser or a process it did not launch.

### Use a dedicated persistent profile

Authentication state may persist across worker restarts, but it is isolated from the user's everyday Chrome profile. Tests receive temporary profiles; the installed product uses an application-support directory outside the source tree.

Authentication uses an explicit control handoff rather than cookie import, stealth automation, or a guessed login boolean. The controller prepares the target under Playwright, captures only a keyed semantic fingerprint and sanitized route, closes the controlled context, waits for the profile to unlock, and launches the same isolated profile as a native browser process. Chromium control and native handoff both pin the same `Default` partition inside the same user-data directory; Firefox uses the same explicit profile root. The resolved executable, application name, backend, executable source, user-data directory, profile directory, and effective profile path form one launch identity.

The native window receives a static Stage5 identity-marker tab next to the requested login tab, while the handoff result names the browser application's real on-screen identity and a short label. This is important when separate agents have simultaneous Stage5 handoffs under different backends. The user completes credentials/passkey/CAPTCHA/OTP privately. Chromium-family instructions say to leave the application open; Firefox instructions say to quit normally.

Agent browser operations are unavailable during the private phase. For Chromium, the native launch includes a fixed ephemeral debugging port bound to `127.0.0.1`. Its endpoint and exact port are internal, never returned to an agent or journaled. Resume requires that exact owned process to remain alive, connects with Playwright over CDP, and verifies the browser-reported profile path before allowing account work. Because the process never restarts, in-memory session cookies stay inside the same browser. A `0600` profile-local record contains the backend, owned PID, port, lifecycle state, version, creation time, and—only after control resumes—an opaque selected-target identity plus an optional bounded privacy-safe last-action diagnostic bound to that target and an opaque main-document identity. It contains no raw page content, entered value, request payload, query, fragment, credential, or cookie and is never returned or journaled. A new worker passively reconstructs `awaiting_user` only when that v1 record and either the canonical durable lease or the narrower crash-window proof bind the exact executable, profile, process-start identity, unique loopback endpoint, and marker. Passive status never attaches; only explicit resume may claim control. After explicit resume marks the record `controlled`, compatible worker replacement can reconnect.

Firefox retains restart-based resume. It refuses a running process, remaining profile lock, launch-identity mismatch, or a caller-supplied non-root post-login route that cannot be reached after the human phase added target-origin session metadata. Current-session process evidence governs its shutdown gate: exit code zero plus no signal and zero locks permits reattachment. If the process exit is abnormal or unavailable but the process is gone and locks are clear, the first resume reports a bounded override and one deliberate second resume reattaches the same profile. It never deletes locks, edits exit preferences, or selects cookie values.

Once allowed, the controller captures privacy-safe target-origin storage at the first controlled instant and after target load. Chromium's first controlled instant is the same running native process; Firefox also retains its offline-after-exit checkpoint. Stage5 records the initial `navigator.webdriver` observation and the actual Chromium Profile Path obtained from a live Chromium diagnostics surface. Filesystem aliases are canonicalized for comparison while both configured and observed paths remain visible. Cookie keys are hashed only for in-process set comparison and values are never read or returned. The controller then removes the marker tab and returns a bounded semantic preview. A fresh full semantic snapshot remains required to prove site-specific signed-in state. Exact human clicks and private-phase network traffic are intentionally unobservable.

Compatible worker updates are deferred while the private handoff is active. After Chromium attachment, a graceful worker shutdown disconnects only the CDP client and leaves the owned browser running; the replacement worker reads the private control record and reconnects. Explicit `browser_stop` closes that owned browser and removes the record.

### Preflight and switch browsers

The MCP host defines an initial default browser through trusted startup configuration. A joined agent's last successfully established backend then becomes that agent's durable selection across MCP-host reconnects; YouTube's Chrome selection and Finance's Brave selection remain independent rather than competing through one global last-browser value. An agent can inspect the fixed backend registry with `browser_available` and explicitly change the active isolated profile with `browser_switch`. The controller proves the target executable is available before it closes the current context, and the supervisor remembers a successful selection when replacing a failed worker.

Chrome, Brave, and Edge are resolved from allowlisted product installation locations, with an absolute executable-path override available only to the operator. Chromium, Firefox, and WebKit use pinned Playwright runtimes. Each backend receives a separate Stage5 Browser profile by default. This prevents profile locking and avoids mixing authentication state between products while retaining the original bundled-Chromium profile location for existing users. Chromium-engine launches explicitly enable Chromium sandboxing on macOS; diagnostics expose the safe policy decision rather than the raw process command line.

### Commit-first navigation

Navigation waits for network commit, then performs separately bounded readiness and client-redirect stabilization probes. Results distinguish requested and final sanitized URLs, include the server redirect chain and observed main-frame URL changes, and classify non-2xx responses as structured warnings. A page that committed successfully is not reported as a total failure merely because a later lifecycle event was lost or delayed, but commit alone is not treated as proof that the requested workflow state was reached.

### Semantic targeting

The primary action tools use ARIA roles and accessible names. They require a unique match and reject ambiguity. A semantic snapshot uses the unique active visible modal as its root when one can be established, so surrounding application depth does not hide portal controls. Multiple unresolved modals produce a warning and a document snapshot instead of an arbitrary choice. Popup options and selection surfaces that are CSS-visible but clipped outside the viewport are removed from the returned semantic tree; an offscreen popup-backed scroll surface is likewise withheld, while ordinary offscreen page refs remain available for exact-node viewport preparation. Each single capture issues one random snapshot ID and Playwright element-reference map; reference clicks require that exact latest snapshot, frame, document version, and observed ref. The capture retains a privacy-safe role/name descriptor, a direct link's already-observed destination when present, and the exact modal/document scope for each ref. After necessary pre-input activation, a disappeared ARIA ref may bind only one exact role/name-equivalent control inside that retained scope, and an observed link destination must also match; scope replacement or multiple matches fail before dispatch. The same destination check applies to article-scoped virtualization recovery and never enters diagnostics or journals. The same capture separately inventories a bounded set of hidden HTML file inputs and binds each opaque ref to the exact observed element handle. Any attempted action or navigation invalidates both capability sets. A role target that detaches during scrolling may be resolved once more only before any input has occurred. Ordinary native buttons and button-shaped options use the guarded pointer engine so framework keyboard focus cannot substitute an active-first choice. A native button uses one preselected guarded keyboard transport only with a non-null bounded postcondition: Enter by default, or Space when the requested visible effect is a menu/list option role. No transport changes after input, and every partial sequence is reconciled as non-retriable rather than rebound or replayed.

Clicks can carry bounded URL, selected-state, visible-element, and exact hidden-element postconditions. Selected state includes the accessible selected, checked, pressed, current, and expanded states, so custom popups do not require a site-specific modal role. An option or popup-surface `expectedVisible` check requires a unique target that is both CSS-visible and intersecting the viewport after overflow clipping; a dormant offscreen portal cannot prove that an opener succeeded. `expectedHidden` passes when the exact semantic lookup has no match or every match in the bounded candidate set is hidden. Any visible match fails; an over-limit set, missing frame, or observation failure remains unknown. Returned checks contain booleans/null only and omit the supplied semantic name. The final deadline-bound poll is always reconciled, so a state change during its last wait is not missed. When partial exact-target input has already occurred, an observed requested effect is terminal success with the original partial dispatch evidence; otherwise the operation remains explicitly non-retriable.

Control inspection may deliberately reveal custom option surfaces, so `revealOptions=true` is a reversible-view action rather than a pure read. One bounded discovery owner enumerates semantic popup roles and generic rendered option groups behind positioned/popover/dialog boundaries, retaining the innermost real scroll surface when present. If a broad positioned portal contains strict option branches separated by a bounded visual gap, those branches become distinct candidate surfaces; adjacent item wrappers remain one popup. Popup association prefers explicit/structural proof, then focused, expanded, and spatial tiers. Multiple candidates within a non-structural tier resolve only through one decisive normalized edge-gap lead. The spatial tier alone may exclude materially overlapping siblings when `elementFromPoint` inside the overlap proves the popup surface covers them and the surviving exterior anchor is tightly adjacent; uncovered overlap, structural contradictions, and positional ties stay ambiguous. DOM count is not semantic ownership: nested target-owned surfaces collapse to one outer root, and disjoint target-owned panels are retained as one bounded composite capability. Surfaces with different owners remain ambiguous without input. A proven already-open target surface set is inspected without closing or reopening it, even if another popup is visible. Otherwise one exact competing owner is closed through its own phase and postcondition before one target opener dispatch. The reveal phase reconciles the associated rendered surface set after normal or partial pointer input, so a mouse-down that opens the menu and replaces its React node becomes terminal success with the original partial evidence and no replay. If opener or competing-popup preparation crosses a document replacement, the outer control manager preserves the strongest physical dispatch evidence, aborts all old-document capabilities, and reports `document_changed_during_control_inspection`. The caller reads durable page events and fresh tabs, treats `document_replaced` as possible unsaved-state loss, and never replays the opener. Control results, failures, and fresh-host execution traces expose only the proof tier, bounded candidate-class counts, and decision category; geometry and semantics remain omitted.

Input activation is background-preferred. A controller-selected page whose renderer is already visible is used without `bringToFront` or native application activation. Hidden renderers alone enter exact-page and exact-owned-process recovery. Click preparation establishes this state before binding the final live control, so a reactive page may replace a unique role target—or one fresh snapshot ref with a unique same-scope role/name replacement—during necessary activation and Stage5 will resolve the post-activation control before installing its dispatch guard. Target actionability and guarded page-mouse fallback share one exact-target geometry evaluator. It begins with the element/viewport/overflow intersection, follows slotted/shadow composed ancestry, and permits a bounded browser hit-test override only when a point inside the target's own viewport-clipped client rectangles hits that exact target or its composed descendant. A sibling, ancestor, cover, or unrelated overlay can never turn that inference into contact.

Compatible updates are state preserving. A connected direct-Playwright context defers worker replacement until explicit stop because its unsaved DOM cannot be reconstructed from a URL. A proven native-CDP browser remains running across replacement, and its private control record retains an opaque selected-target identity so the new worker reconnects to the exact tab rather than a duplicate URL. During graceful worker shutdown, Stage5 best-effort retains the existing bounded sanitized last-action diagnostic without changing its already-terminal result. Reattachment restores that diagnostic only when the exact target, opaque main-document identity, and sanitized URL still match; a different tab or document fails closed with no restored action evidence.

Snapshot-bound text input covers unnamed editors without weakening semantic role targeting. The semantic snapshot captures both the exact eligible editor handle and the exact modal/document root handle. `browser_fill_ref` accepts only a ref in the latest snapshot of the same frame/document and uses those retained one-use handles to prove scope containment; it never performs a live ARIA-ref resolution or a global modal rescan during action preparation. It inspects the exact retained handle before viewport preparation: an already-visible in-viewport editor skips movement entirely, while an offscreen editor gets one short, fixed exact-handle DOM scroll followed by normal revalidation instead of Playwright's stability-gated scrolling. One deadline reserves finalization time and records the exact preparation substep, terminal fill phase, target state, and boolean input/change/logical-value evidence in page diagnostics. Multiline contenteditables compare their logical block/line-break text rather than raw DOM `textContent` or layout-expanded `innerText`. The capability is consumed on every attempt, and the supplied value is excluded from results, errors, diagnostics, and journals.

File selection accepts only absolute paths to readable regular files, rejects symlinks and unsupported multiple selection, and calls Playwright's file-input primitive directly rather than exposing the native picker. It captures name/size metadata in a temporary capture-phase input/change listener before application handlers may consume and clear the control, with the retained browser `FileList` as a fallback. The listener is removed immediately, the input capability is consumed once, and a fresh semantic preview is returned. Generic `observationMs` sampling is bounded to 5 seconds; caller-supplied semantic completion/error markers can wait up to 60 seconds within the overall operation timeout. The result distinguishes completion observed, active progress, an error signal, and unverified processing; successful network responses alone never prove completion.

Active-page ownership is explicit during controlled work. A newly created auxiliary page is bound for diagnostics but does not replace a valid agent-selected page. If the active page is lost and exactly one live page remains, the controller selects that sole page synchronously; unique visibility reconciliation remains available for the private-authentication transition where the user may have selected a different tab.

Tab capabilities are random and session-scoped. Passive exact-tab inspection never activates a background renderer. When no modal is visible, a capture may append up to three novel visible outermost article/standalone-quotation detail sections at depth 20, bounded to 30,000 total characters and stripped of every ref. When the caller explicitly requests temporary activation for a hidden loading document, the worker pins both exact pages and the target document, observes bounded generic loader/content evidence, switches only the renderer inside the controlled browser, withholds every action ref, and restores the prior selected renderer in `finally`. It does not invoke native application activation or mutate controller selection, and an unproven restoration fails closed.

Scrolling and rendered-text search use fixed internal operations rather than exposing arbitrary script execution or fragile one-off selectors. Each snapshot independently inventories a bounded set of visible nested vertical or horizontal scroll surfaces, retaining exact element handles behind opaque refs. A targeted scroll validates the latest snapshot/frame/document, consumes the capability once, and operates on that exact element and axis. The default remains the frame document.

Scroll first activates the controller-selected page and requires a visible renderer before measuring its baseline and before each movement step. If activation fails before movement, dispatch is definitely false; if visibility is lost between steps, completed steps are retained and never replayed. One observation root—the exact nested target, one uniquely visible semantic feed, or the viewport—is pinned for the entire operation so virtualized layout changes cannot make before/after counts incomparable. If that exact root detaches, the operation promptly returns structured surface-loss and completed-step evidence; it cannot become false loader disappearance or consume the remaining content wait. Outermost standalone quotations join articles as content units, while nested quotations are not double-counted. Loading-only content shells are represented as unresolved loading indicators rather than rendered units, while statuses inside otherwise substantive content are not treated as placeholder shells. When no explicit semantic loader exists, an exact generic loading-text leaf may be recognized by a bounded scan; disappearance is usable only when that scan remained complete. Candidate processing is internally bounded; exhausting an authoritative semantic limit produces structured incomplete-observation failure instead of saturated counts. The optional animated-empty-element heuristic tracks its completeness separately: it cannot block semantic content growth or explicit loader disappearance, but Stage5 will not infer animation-only disappearance from a truncated scan. Movement and content waiting stop before a reserved result-finalization window.

Scroll output separates selected-surface geometry from document geometry and a semantic timeline end. Boundary comparison allows one CSS pixel because browsers commonly expose fractional scroll offsets against integral layout extents. An optional bounded content wait samples aggregate article-shaped semantic-content and visible loading-indicator counts until content growth, loader disappearance, either condition, or timeout. A downward geometric boundary remains unconfirmed without a caller-supplied visible end marker. No final movement plus earlier growth, a remaining loader, or an unmet requested wait is classified as a stalled dynamic feed. Scroll begins and ends a sanitized page-action window so diagnostics can correlate bounded request classifications without retaining selectors, page text, or raw network data.

Frames are explicit capabilities rather than hidden traversal. `browser_frames` inventories the active page and issues opaque, session-scoped IDs. Snapshots and semantic actions accept one of those IDs, including for cross-origin frames. Detachment or navigation invalidates the ID, forcing the caller to observe current frame state before acting again. Journaled frame URLs are reduced to origin and path.

### Local stdio MCP

The initial product is a local stdio MCP server. It exposes a narrow tool surface and does not open a network listener. Remote operation requires a separate threat model.

## Data handling

The supervisor journal records operation identifiers, names, timings, outcomes, recovery state, and sanitized URL origin/path where useful. It must not record tool arguments, local file paths, DOM/page content, query strings, fragments, headers, cookies, form values, screenshots, or credentials. File-selection results expose only basenames, sizes, input constraints, and bounded processing evidence; absolute paths remain inside the worker call.

Screenshots are captured only through an explicit tool call, stored with restrictive local permissions, and returned only to the invoking MCP client.

Launch diagnostics expose only allowlisted cause categories, selected backend, exact configured and observed runtime profile binding, profile writability/known lock names, build metadata, sandbox policy, control mode, known automation/storage-argument policy, an observed `navigator.webdriver` boolean when a controlled page exists, and static suggested actions. Offline authentication boundaries expose every allowlisted cookie-database location, modification timestamps, and target-origin/session/persistent presence booleans. Cookie-key identifiers are hashed in-process only for phase comparison and are never returned. Controlled cookie results are immediately reduced to domain/name/expiry metadata; values are never read, retained, compared, hashed, logged, or returned. While Chromium is live, SQLite rows are non-authoritative because the browser may hold a valid in-memory cookie jar while migrating stores; live presence therefore comes from the context rather than the open database. Page diagnostics retain bounded category/count/status records for successful, redirected, failed, and HTTP-error requests; they also isolate events whose timestamps fall within the most recent click window. Raw console and exception text is represented only by a process-local keyed fingerprint; request bodies, headers, queries, fragments, form values, and full launch arguments are never retained or returned. The journal may store the allowlisted cause and backend but never the raw launch error or filesystem configuration supplied by an operator.

## Future boundaries

An optional extension may later bridge an explicitly selected existing Chrome profile. It must remain separate from the default dedicated-profile mode. Service adapters, remote supervision, and a desktop status UI are also independent layers rather than browser-core responsibilities.
